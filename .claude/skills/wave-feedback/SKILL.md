# 波フィードバック処理

ユーザーが実機テストで見つけた不具合・要望のリストを受け取り、修正からコミットまでを一括処理する。
対象は単一HTML `寝殿造り3D探訪_統合版.html`（Three.js r128・完全プロシージャル・オフライン動作）。

## 手順

### 1. トリアージ表を作る（最初に必ず提示）

貼られたフィードバックを1件ずつ分解し、次の表にして**修正前にユーザーへ提示**する:

| # | 症状 | 場所 | 重大度 | 種別 | 推定原因（検索アンカー） | 対応 |
|---|---|---|---|---|---|---|

- 重大度: 進行不能 / 目立つ / 軽微 / 要望（ops/FEEDBACK_TEMPLATE.md の定義に従う）
- 種別: バグ修正 / 表示調整 / 音 / バランス / 新規要望
- 推定原因は PROJECT_MAP.md の検索アンカー（`クイズモード`、`メインループ` 等）で示す。行番号は使わない。
- **解釈が複数ありうる項目・大規模改修になる要望は AskUserQuestion で確認してから着手**する。
  それ以外は確認を待たずに修正へ進んでよい。

### 2. 修正する

- 処理順: 進行不能 → 目立つ → 軽微。「要望」で工数が大きいものは修正と混ぜず、最後に計画として提案する。
- **進行不能バグは1件ずつ独立コミット**（後で単独revertできるように）。軽微はまとめてよい。
- 編集規約（PROJECT_MAP.md §6 / HANDOFF_LATEST.md §1）を厳守:
  - r128 の旧カラーAPI（`outputEncoding`/`sRGBEncoding`/`texture.encoding`）を維持。新 `colorSpace` API 禁止。
  - 外部CDN追加禁止。単一ファイル・オフライン完結を壊さない。
  - 共有ホットスポット（`ITEMS`/`register()`/`animate`/`SFX`/`AmbientAudio`/`TIMES`/`QUALITY`/`BLOOM`/`GFX`）を触るときは影響範囲を明記。
  - 全画面をロックするUI（過去に起動不能を起こした初回チュートリアル型）は作らない。

### 3. 検証する

- 各修正後（最低でもコミット前に1回）: `npm run preflight`
- 描画・負荷に関わる修正は `npm run preflight:bench` で before/after を採取し、差分をコミットメッセージか BENCHMARKS.md に記録。
- FAIL のまま次の修正に進まない。

### 4. コミットする

- メッセージ形式は既存慣行に合わせる: `波X: 実機FB第N弾（対応内容の要約）` または `fix: 概要`。
  波の記号（A, B, … Z, AA, AB…）は直近のコミットログから次を採番する。
- push は現在の作業ブランチへ。**main へ直接 push しない**（mainはPages自動デプロイに直結）。

### 5. 完了報告

最後に次の形式で報告する:

- ✅ 修正済み: （#と一言ずつ）
- ⏭️ 見送り/要判断: （理由つき）
- 📋 実機で再確認してほしい項目: （確認手順つき。公開URLで見る場合はキャッシュ回避 `?v=コミットハッシュ` を付ける）
- 📝 新規要望として積んだもの: （次の波以降の計画）
