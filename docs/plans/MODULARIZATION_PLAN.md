## 2. リスク階層と実装順序

### Tier 1 — 純データ抽出（低リスク・既存パターンで実証済み）
実装は `items.js` と同型の「マーカー2行挿入＋バイト同一往復＋`--check`」で行う。**この階層だけを 7/13 目標のスコープとする。**
1. `WAKA_DATA`（+`_WAKA_NUM`/`_WAKA_SN`）→ `src/app/waka.js`
   - 注意: 直後の登録 `forEach`（4181-4189）は**ロジックなので本体に残す**。抽出は `const WAKA_DATA=[...];` の宣言のみ。実行順序（ITEMS定義後→WAKA読込→forEach登録）を壊さない。
2. `QUIZ_POOL` → `src/app/quiz-pool.js`
   - 注意: `verify:html` がITEMSキー集合との整合を検証している。分離後もこのチェックを維持。
3. （任意）`SOUNDSCAPE`、`ONMYO_DIV_*` → 効果は小さいが同パターンで安全。時間があれば。

### Tier 2 — ベンダー分離（中リスク・最大のバイト削減）
Three.js コア＋postprocessing（23–1051）→ `src/vendor/three-r128.js` 等。
- 効果: 5.2MBの大部分。クローン/エディタ負荷が激減。
- リスク: `file://` オフライン動作（L24明示要件）を壊さないこと。ビルドで必ず再埋め込みし、`verify:html` の「r128 API存在」チェックを通す。CDN参照への置換は**禁止**（オフライン要件違反）。
- 独立PRで慎重に。Tier 1完了後に着手。

### Tier 3 — ロジック分割（高リスク・当面見送り）
`APP`（559参照）・`animate`（673行）・`GISSHA_YARD`・各モード関数群。
- これらは実行順序とグローバル状態に密結合。単純なテキスト抽出では壊れる。
- 分割するならESモジュール化＋バンドラ導入という別プロジェクト規模の判断になる。**現時点では非推奨**。単一HTML方針とオフライン要件を考えると、費用対効果が合わない。

## 3. 共通ビルド基盤の到達点（manifest駆動）

現在は `build-app-css.js` / `build-app-items.js` と個別スクリプトが並ぶ。Tier 1で対象が4〜5個になった時点で、以下へ収斂させる:

- `scripts/app-manifest.json`: `[{ name, marker, src, kind }]` の宣言的リスト（css / items / waka / quiz …）。
- `scripts/build-app.js`: manifestを読み、各ブロックに対して `--extract` / 既定=注入 / `--check` を実行する汎用ドライバ。個別ロジック（境界特定＝ブレースマッチャ等）は kind ごとの小関数に分離。
- 既存の個別スクリプトは新ドライバへの薄いラッパとして残す（後方互換・CI/手癖を壊さない）。
- `npm test` と CI は `build:app:check`（全ブロック一括同期チェック）1本で担保。

**設計原則（不変）**: どのブロックも「マーカー除去後の再構成が原本とmd5一致」を必須ゲートにする。1バイトでも変えない。

## 4. 進め方

1. Tier 1 を1ブロック=1PRで進め、各PRで CI（verify＋実機smoke）を通す。
2. 対象が揃ったら §3 の manifest駆動へリファクタ（これも1PR）。
3. Tier 2 は独立判断で。Tier 3 は当面着手しない。
4. 各実装は Opus のサブエージェントに委譲可。ただし**バイト同一性の検証結果レビューはオーケストレーターが行う**。
