# QA戦略 — 寝殿造り3D探訪

最終更新: 2026-07-12
目的: モジュール分割（`MODULARIZATION_PLAN.md`）を今後何十回も安全に回すための「回帰を捕まえる網」の設計。実装より**何を検証すべきかの設計**を先に固める。

## 1. 現状の網（2026-07時点）

| 検証 | 捕捉できるもの | 捕捉できないもの |
|---|---|---|
| `build:app:css:check` / `build:app:items:check` / `build:story:check` | ソースと本体HTMLの同期ズレ（分離ビルドの命綱） | 実行時の挙動 |
| `verify:html` | DOM/JS構造・ITEMS・WAKA100首・音源参照・r128 API の静的存在 | 動かした時の破綻 |
| `verify:story` / `verify:routes` | 章構造・ED到達性・ルートバランス | 実際のプレイ体験 |
| `smoke`（Playwright） | 起動・全モード開始・音ON/OFF・季節時刻切替（＝クラッシュしないこと） | 各モードの「クリア」まで／性能 |

**穴**: 現状のsmokeは「起動して各モードが**開始**できる」ことの確認に留まる。モードを**遂行**した時の破綻（退治で勝てない、物語EDに到達できない、図鑑が解放されない）と、**性能劣化**（fps低下・ロード時間増）は捕捉できない。分割作業はまさにこの領域を壊しうる。

## 2. 強化の設計（優先度順）

### S1. シナリオ・スモーク（モードを遂行する）
現行smokeを拡張し、各モードで「開始→代表的操作→期待状態」まで到達させる。実装は `scripts/smoke-playwright.js` に per-mode ステップを追加。

| モード | 遂行シナリオ | 期待state（`window.APP`等から観測） |
|---|---|---|
| クイズ | 出題→正答クリック→次問 | スコア加算・出題プールがQUIZ_POOL由来 |
| 垣間見 | 観察地点到達→巡回回避→観察成立 | ミッション達成フラグ |
| 物の怪退治 | ボス出現→破魔の矢命中→撃破 | ボスHP0・勝利HUD |
| 物語 | 章開始→選択肢→ED到達 | いずれかのEDIDに到達（verify:routesと別に実挙動で） |
| 図鑑 | 対象クリック→登録 | 該当ITEMSキーが解放状態 |

- 観測は本体に既にある `window.APP`・`window.__*`（例: receipt同様のテストフック）を使う。無ければ最小限の観測用フックを本体に足す（表示に影響しない読み取り専用）。
- CIの `smoke` ジョブに載せる（既にPlaywright chromium導入済み）。

### S2. 性能予算（回帰を数値で捕まえる）
`docs/metrics/BENCHMARKS.md` と `scripts/collect-benchmark.js` が既にある。これを予算化する。
- 予算例: 初期ロード〜操作可能まで N 秒以内、代表シーンの平均 fps ≥ M、メモリ上限 X。
- `scripts/collect-benchmark.js` に閾値判定を追加し、超過でCIを警告（最初はfail-softで基準値を蓄積→安定後にfail）。
- ベンダー分離（Tier 2）の前後で必ず取得し、退行がないことを確認。

### S3. 抽出安全ネット（分割専用）
分割PRで最も効くのは既存の「バイト同一性＋`--check`」。これは維持。加えて:
- 各データ抽出後、`verify:html` の該当チェック（WAKA100首・ITEMSキー）が緑であること＝データ欠落の即時検出。
- manifest駆動化（計画§3）後は `build:app:check` 1本で全ブロックの同期を保証。

## 3. 実装順序

1. **S1 シナリオ・スモーク**を先に入れる（分割で最も壊れやすい「遂行」を守るため）。1モードずつ追加しCIを緑に保つ。
2. **S3**は分割PRごとに既存チェックで担保（追加実装ほぼ不要）。
3. **S2 性能予算**はベンダー分離（Tier 2）着手前に基準値を取る。

## 4. 委譲方針
- S1のシナリオ実装はテスト観点の設計が要るため、シナリオ表（本書§2.1）を渡してOpusに委譲可。
- 観測フックを本体へ足す場合は最小・読み取り専用に限定し、`verify:html`とsmokeを通す。
- **合否基準（何を"クリア"とみなすか）の決定はオーケストレーターが行う**。
